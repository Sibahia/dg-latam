# End-to-End Code Audit

**Audit date:** 2026-08-07  
**Audited revision:** `acb2638` / `v1.27.0`  
**Report target version:** `1.27.1`  
**Audience:** Maintainers and operators. This document contains security and abuse details and should be treated as private until the critical findings are fixed.

## Executive summary

The current multiplayer server should not be exposed to untrusted clients. Four independent account/session takeover paths were confirmed, and the game server still accepts client-authored damage, health, entity, reward, talent, and social state in ways that allow cheating or disruption of other players.

The most urgent issue is not a subtle cryptographic weakness: both login opcodes deliberately discard the supplied password. Any caller that knows an account email can authenticate as that account, and an unknown email is silently registered. The repository already contains a regression test for the intended password behavior; it currently fails.

The audit also found guessable 16-bit transfer tokens that can replace a connection's user and character, unauthenticated Discord account linking selected by email, and Discord OAuth completion bound to a shared/spoofable IP address rather than a browser/game-session challenge. These paths must be repaired together because fixing only password login would leave alternative account takeover routes.

Multiplayer authority is incomplete. A client can submit arbitrary power-hit and damage-over-time values, damage another player without a PvP rule, inflate its maximum health through respawn, teleport through absolute entity updates, remove shared entities, forge reward sources, allocate unearned talent/crafting points, and accept a party invitation that was never issued. One of those entity-destruction failures is reproduced by the existing multiplayer regression suite.

The automated baseline is also red: 4 of 92 regression files fail, and the client-patch verifier confirms that the forge-tutorial persistence patch is absent from the served SWF. CI currently runs only typecheck and build, so it does not prevent either regression class from reaching production.

## Scope and method

The audit covered the maintained application end to end:

- 303 tracked TypeScript files and 80 tracked JavaScript files (133,717 lines total)
- TCP framing, packet dispatch, authentication, transfer and session lifecycle
- multiplayer entity, combat, party, dungeon and reward authority
- account, character and save persistence on JSON and MongoDB backends
- HTTP, Discord OAuth/linking, presence and administration integrations
- deployment container, production scripts, CI, dependencies and configuration
- 93 tracked regression files and 135 tracked client patch scripts
- JSON game data and the scripted integrity checks for compiled Flash assets

Compiled SWF/SWZ files were not manually decompiled as a substitute for source review. Their integrity was assessed through the repository's patch verifiers. Thirty-seven FFDec-dependent checks could not run because FFDec is unavailable on the audit host; those assets are explicitly unverified, not presumed correct.

Severity means:

- **Critical:** practical account/session takeover or compromise of the multiplayer trust boundary
- **High:** cross-player disruption, unrestricted progression/economy abuse, or likely save corruption
- **Medium:** meaningful correctness, availability, privacy, release, or conditional security risk
- **Low:** defense-in-depth, development-only exposure, or maintenance/release-integrity weakness
- **Informational:** verified status or a recommendation without a presently demonstrated defect

## Detailed findings

### AUD-001 — Critical — Password authentication is completely bypassed

**Evidence:** `src/server/handlers/LoginHandler.ts:401-438` parses a login payload but keeps only `email`. `handleLoginCreate` creates an empty password record and authenticates immediately. `handleLoginAuthenticate` auto-creates an unknown email and also authenticates immediately. The imported password verification helpers are unused. `test/login_password_auth_regression.ts` fails at its first assertion because direct registration authenticates the client.

**Impact:** Anyone who knows or guesses an existing email can take over its characters and saves. Attackers can also create unlimited accounts. Password challenge, hashing, wrong-password rejection and the intended Discord-controlled account-creation policy are all bypassed.

**Recommended fix:** Disable direct game registration unless a separately authenticated enrollment flow explicitly enables it. On authentication, require an existing account, validate input bounds, unmask the challenge response, verify it using the stored password record with a constant-time comparison, and consume/rotate the challenge after every attempt. Add per-account and per-IP attempt throttles, generic error messages, and lockout/alert telemetry. Do not preserve the email-only record as a compatibility fallback for multiplayer accounts; require an explicit migration/reset.

**Required tests:** Keep `login_password_auth_regression.ts` in CI and add socket-level tests for replayed challenges, unknown accounts, legacy records, concurrent attempts, rate limits, and successful Discord-created account login.

### AUD-002 — Critical — Guessable transfer tokens can assume another character session

**Evidence:** `src/server/core/TransferTokenAllocator.ts:5-84` allocates from only 65,536 values using `Math.random()`. `CharacterHandler.handleGameServerLogin` at `src/server/handlers/CharacterHandler.ts:1173-1203` accepts a token from an unauthenticated packet and assigns the pending entry's `character`, `userId`, account stub, token and target level to the caller. `LevelHandler.recoverTransferSessionStateFromExactToken` at `src/server/handlers/LevelHandler.ts:4735-4813` can clone an active session or directly replace the caller's character and user from a used token. Neither path binds the presented token to the authenticated account or originating connection.

**Impact:** A remote client can enumerate the small token space and steal a character during login or level transfer. Recovery from active and used tokens expands the useful window beyond a single pending transition. The stolen session can mutate the victim's save.

**Recommended fix:** Replace protocol-visible numeric tokens with at least 128 bits from `crypto.randomBytes`, or use an opaque signed ticket if the legacy packet can carry it. Bind each ticket to user ID, character ID, source connection/session nonce, exact destination and expiry. Consume it atomically once. A transfer recovery path may recover only state already owned by the authenticated caller; it must never copy identity from the token into an unrelated client. If the wire format cannot carry sufficient entropy, add a second authenticated challenge packet before applying state.

**Required tests:** Simulate two clients where one presents the other's pending, active, used and aliased token; every attempt must be rejected without changing identity. Test replay, expiry, destination mismatch and simultaneous consumption.

### AUD-003 — Critical — Unauthenticated Discord linking can target an arbitrary account

**Evidence:** `src/server/core/StaticServer.ts:874-921` exposes `/discord/link` and `/api/discord/link/start`. A caller supplies `?email=...`, or the server guesses an account by requester IP, then calls `DiscordAccountLinkService.createAuthorizeUrl`. `src/server/integrations/DiscordAccountLinkService.ts:205-244` looks up that unlinked account and creates signed link state containing its email/user ID. The comment in `createAuthorizeUrlForState` says linking requires an authenticated account, but the HTTP route supplies the account without authentication.

**Impact:** Knowing an unlinked game email is enough to start a valid OAuth flow and bind the attacker's Discord identity to the victim's game account. That link can become a durable recovery/login mechanism even after password authentication is repaired.

**Recommended fix:** Remove the email selector from public link-start routes. Issue a one-time link nonce from an already authenticated game session, bind it to user ID and connection/session ID, expire it quickly, and atomically consume it on OAuth callback. Re-read the account and verify it is still unlinked at completion. Require reauthentication for relinking and audit every link transition.

**Required tests:** An unauthenticated request, an authenticated request for another user, a replayed nonce, an expired nonce and a concurrent double-link must all fail.

### AUD-004 — Critical — OAuth auto-login is IP-bound, replayable, NAT-unsafe and proxy-spoofable

**Evidence:** `StaticServer.authenticateRequesterLoginClient` at `src/server/core/StaticServer.ts:250-270` authenticates the latest unauthenticated game socket whose remote IP matches the HTTP request. If no socket is found, `GlobalState.rememberDiscordOAuthLogin` stores the account by IP for two minutes (`src/server/core/GlobalState.ts:428-441`). `LoginHandler.handleLoginVersion` uses `peekDiscordOAuthLogin`, not the existing consuming method, at `src/server/handlers/LoginHandler.ts:376-397`, so the credential is reusable. `StaticServer.resolveRequesterAddress` at `src/server/core/StaticServer.ts:428-438` always trusts `X-Forwarded-For`; the documented `TRUST_PROXY_HEADERS` setting is not implemented.

**Impact:** On shared NAT, the wrong household/client socket can receive another person's authenticated account, and repeated connections can reuse the pending login. When the service is directly reachable, a caller can spoof proxy headers in HTTP flows that choose a game socket or expose pending account data. Mobile/VPN address changes also make legitimate login unreliable.

**Recommended fix:** Bind OAuth state to a cryptographically random browser nonce and a separate random challenge displayed or delivered over the exact game connection. Store only a hash server-side, include the intended connection/session ID and user ID, and consume atomically once. Never use source IP as identity. Configure Express proxy trust only for known proxy addresses; otherwise ignore forwarded headers. Remove email/user ID from the public pending response.

**Required tests:** Two clients behind one IP, two IPs with spoofed forwarding headers, replay, callback-before-socket, socket-before-callback and concurrent callbacks must select only the intended connection once.

### AUD-005 — High — Clients author damage and can attack other players without a PvP rule

**Evidence:** `parsePowerHitRelayInfo` reads a client-supplied damage value (`src/server/handlers/CombatHandler.ts:4646-4666`). `handlePowerHit` then applies that value to an NPC or any player session in the same level (`src/server/handlers/CombatHandler.ts:5280-5468`). Source ownership and cast-rate checks exist, but there is no server derivation of damage, cast-to-hit nonce, range/line-of-sight validation, team/PvP rule, or target consent. Damage-over-time packets follow the same pattern at `src/server/handlers/CombatHandler.ts:6599-6705`. Hostile HP reports in `handleCharRegen` also accept client negative deltas for supported bosses.

**Impact:** A modified client can one-shot mobs and bosses, manufacture completion/reward eligibility, or kill another player in a non-PvP zone. A rate limiter changes only how often a forged hit is sent, not its value or legality.

**Recommended fix:** Make the server own cast state, target legality, range and damage calculation. A cast should create a short-lived server nonce with source, power, allowed targets/timing and computed damage bounds; hits must consume or advance that state. Explicitly deny player targets unless a server-owned PvP mode/team rule permits them. Treat client HP reports as observations used only for correction/telemetry, never as proof of damage or death.

**Required tests:** Forged damage, hit-without-cast, duplicate hit, impossible range, wrong power, foreign source, friendly player target and negative/overflow values must not alter canonical HP or rewards.

### AUD-006 — High — Client-created reward sources permit unlimited progression

**Evidence:** `EntityHandler.handleEntityFullUpdate` accepts client-created non-player entities and stores them as client-spawned (`src/server/handlers/EntityHandler.ts:3825-4060`). `RewardHandler.handleGrantReward` accepts client `exp`, `petExp`, `hpGain` and `gold` fields (`src/server/handlers/RewardHandler.ts:1276-1325`). `maybeOverrideDungeonReward` begins with those packet values at `src/server/handlers/RewardHandler.ts:886-991`. Outside server-authority hostile contexts, an entity only needs to look hostile for `legacy_enemy_reward`; there is no canonical death requirement. Processed-source deduplication is ineffective against unlimited forged unique entity IDs.

**Impact:** A client can create arbitrary hostile sources and grant itself repeated XP, gold and loot. This corrupts progression and any shared economy/ranking assumptions.

**Recommended fix:** Allocate reward sources exclusively from server-owned spawn/death records. Compute XP, gold, health and drop rolls from immutable server game data. Require an atomic, one-time death/chest nonce tied to a canonical entity and eligible recipients. Never accept reward amounts or source classification from the client. Put hard caps on pending loot and processed-source state.

**Required tests:** Live source, unknown source, client-spawned source, duplicated source, forged amounts, forged coordinates and a large sequence of unique IDs must produce no reward or unbounded state.

### AUD-007 — High — Respawn and regeneration permit HP inflation and foreign mutation

**Evidence:** `handleRespawnBroadcast` at `src/server/handlers/CombatHandler.ts:5962-6030` accepts an arbitrary entity ID and heal amount. For self it chooses `max(clientHealAmount, intendedRespawnHeal)`, then increases entity and `client.authoritativeMaxHp` to the submitted heal. For non-self entities it can mark shared entities active and overwrite HP unless they match a narrow server-authority NPC guard. `handleCharRegen` at `src/server/handlers/CombatHandler.ts:6337-6404` accepts any positive self delta up to the now-authoritative maximum without verifying a regen tick, buff or source.

**Impact:** A player can heal to full at will, inflate maximum health (within wire limits) and potentially resurrect or alter another non-guarded entity. Inflated HP persists in the live authority state and compounds combat abuse.

**Recommended fix:** Accept respawn only for the caller's own dead entity and only when a server-owned pending respawn record exists. Compute the exact heal and max HP from authoritative stats; ignore packet values. Bind potion consumption and respawn broadcast to a one-time nonce. Drive regeneration from server timers/buffs and treat client ticks as acknowledgements at most.

**Required tests:** Overheal, foreign entity, live-player respawn, duplicate respawn, missing potion, early regen and forged max-HP attempts must be rejected and corrected to the client.

### AUD-008 — High — Absolute full updates bypass movement authority and allow entity injection

**Evidence:** `EntityHandler.handleEntityFullUpdate` takes absolute position, velocity, team, entity type and state from packet `0x08` (`src/server/handlers/EntityHandler.ts:3825-4055`). For the caller's player it writes the submitted position, remembers it as a confirmed spawn, and resets `MovementAuthority` to the new coordinates instead of validating displacement. For non-player IDs it creates entities without a per-client count/ID/type/rate budget.

**Impact:** Incremental movement checks can be bypassed with repeated full updates, enabling teleporting and forged spawn points. Unique non-player updates can consume memory, pollute shared level state, create fake combat/reward sources and amplify broadcasts.

**Recommended fix:** Permit a player full update only during a server-owned spawn/resync window with an expected spawn region and one-time transition ticket. Ignore client team/stats/state fields. Validate subsequent absolute positions through movement authority. Permit client visual proxies only from an allowlisted server spawn plan, with ownership, type, room and count limits; reject arbitrary IDs.

**Required tests:** Mid-session teleport, foreign player identity, hostile flood, invalid type/team, duplicate IDs and full-update movement after a rejected delta must not reset authority.

### AUD-009 — High — Entity destroy can remove live canonical or player entities

**Evidence:** `CombatHandler.handleEntityDestroy` begins at `src/server/handlers/CombatHandler.ts:5620` and resolves the submitted entity but does not apply a general ownership/lifecycle check before later deletion and relay paths. The existing `jc_mini1_server_authority_regression.ts` fails with `early local destroy must not remove live canonical enemy`. Player entities are also relay-eligible and do not receive a universal sender-owns-target check.

**Impact:** A malicious or merely predictive client can delete a live shared enemy before authoritative death and break dungeon progression for a party. It may also make another player's entity disappear from canonical/viewer maps.

**Recommended fix:** Centralize an entity lifecycle state machine. Only the server may transition canonical entities to destroyed. A client destroy request must identify its owned local proxy and match a previously finalized canonical death nonce; otherwise send a corrective snapshot. Player removal must occur only through that player's disconnect/transfer lifecycle.

**Required tests:** Retain the failing early-destroy case and add foreign player, foreign proxy, duplicate, unknown, stale-alias and late-packet cases with two clients.

### AUD-010 — High — Talent, forge and building progression is not server-authoritative

**Evidence:** `TalentHandler.handleAllocateTalentTreePoints` writes the submitted nodes without comparing allocated points to earned points (`src/server/handlers/TalentHandler.ts:102-154`). Non-instant talent training sets ready time to `now` and completes immediately, and `handleTalentClaim` has no ready-time check (`src/server/handlers/TalentHandler.ts:161-263`). `ForgeHandler.handleAllocateMagicForgeArtisanSkillPoints` directly stores five submitted four-bit values without an earned-point budget (`src/server/handlers/ForgeHandler.ts:966-974`). `BuildingHandler.handleBuildingClaim` applies a pending rank without checking `ReadyTime` (`src/server/handlers/BuildingHandler.ts:273-292`). Active master-class changes similarly lack an unlock check.

**Impact:** Modified clients can allocate unearned combat/crafting bonuses, bypass research/build timers and equip unowned disciplines. These values are persisted and affect multiplayer power.

**Recommended fix:** Store total earned/spent points and validate node IDs, prerequisites, per-node caps and totals against server data in one transaction. The server must compute all ready times and reject claims before expiry. Validate discipline ownership/unlocks. Return an authoritative snapshot on every rejected mutation.

**Required tests:** Over-allocation, invalid node, prerequisite bypass, future-time claim, duplicate claim, clock boundary, arbitrary master class and packed forge points above the earned budget.

### AUD-011 — High — Public presence data can force another character into a party

**Evidence:** `/api/presence/sessions` and `/api/presence/discord-target` are unauthenticated (`src/server/core/StaticServer.ts:827-857`). `PresenceService.toSnapshot` includes party IDs, leader, lock state and a signed `joinSecret` (`src/server/core/PresenceService.ts:239-325`). `/api/presence/discord-join` accepts that secret plus an arbitrary `requesterName` (`src/server/core/StaticServer.ts:951-991`), and `SocialHandler.joinPartyFromDiscord` looks up and mutates that online character without authenticating the HTTP caller (`src/server/handlers/SocialHandler.ts:1214-1300`). Join secrets have no expiry and remain derivable for the lifetime of a party.

**Impact:** Anyone who can reach the HTTP server can enumerate online players/locations, obtain an open-party secret, and force a chosen online character into that party. This is a privacy leak and cross-player state mutation.

**Recommended fix:** Do not return join secrets from public presence endpoints. Authenticate the Discord/local bridge with a scoped service credential, and bind a short-lived one-time join ticket to the requester account/character and target party. Minimize public presence fields or require opt-in. Add expiry and key rotation to any signed invite.

**Required tests:** Anonymous enumeration/join, arbitrary requester name, replay, expired secret, renamed leader and locked/full party.

### AUD-012 — High — Party acceptance is not bound to a pending invitation

**Evidence:** `handleGroupInvite` sends a query containing the inviter entity ID but records no pending party invitation (`src/server/handlers/SocialHandler.ts:1628-1680`). `handleQueryMessageAnswer` accepts any submitted entity ID, resolves that online player, and creates/joins its party (`src/server/handlers/SocialHandler.ts:1682-1739`). Guild/friend prompts have their own handlers, but the party fallback has no token, inviter/invitee binding, TTL or one-time consume.

**Impact:** A client can fabricate an accepted response for an arbitrary online player and join/create their party without being invited. Party membership controls shared dungeon scope, progression and social visibility.

**Recommended fix:** Record a cryptographically random pending invite with inviter, invitee, intended party, leader status and expiry. Put that token in the prompt response, consume it atomically, and re-check both parties, dungeon state, lock and capacity on acceptance.

**Required tests:** No invite, wrong inviter, wrong invitee, replay, expiry, leader change, party lock/full and overlapping guild/friend prompt IDs.

### AUD-013 — High — Concurrent save operations can lose updates

**Evidence:** `JsonAdapter.saveCharacterSnapshot` loads the complete character array before entering the per-path save queue (`src/server/database/JsonAdapter.ts:696-710`). Two callers can therefore read the same old array and last-write-wins. Mongo persistence replaces the complete `characters` array with one `$set` and no revision/CAS (`src/server/database/MongoGameDataAdapter.ts:438-455`). Multiple live/reconnecting sessions and asynchronous deferred saves can overwrite unrelated character mutations.

**Impact:** Legitimate concurrent gameplay, reconnects, admin grants or handler saves can silently lose inventory, mission, currency or character changes. The authentication/session findings make concurrent sessions especially easy to create.

**Recommended fix:** Serialize the entire JSON read-modify-write operation per user, not only its final write, and preserve atomic temp-file rename. In MongoDB, store characters as separate documents or update a specific character with array filters plus a monotonically increasing revision. Use compare-and-swap/retry or transactions for currency/inventory operations. Enforce one authoritative live writer per character.

**Required tests:** Concurrent updates to two characters, two fields on one character, deferred save versus immediate save, reconnect overlap, admin grant overlap and injected write failure.

### AUD-014 — Medium — Character creation lacks validation and atomic uniqueness

**Evidence:** `CharacterHandler.handleLoginCharacterCreate` at `src/server/handlers/CharacterHandler.ts:844-910` checks only that `userId` exists and that a prior lookup says the name is free. It does not require `authenticated`, enforce the advertised eight-character-slot limit, validate name length/format/control characters, restrict class/customization to templates, or reject an unknown class fallback. Mongo's character-name index is non-unique (`src/server/database/MongoGameDataAdapter.ts:116-120`), so the lookup-then-save sequence races across accounts.

**Impact:** Accounts can create unlimited or malformed characters and duplicate case-insensitive names under concurrency. Duplicate names corrupt global social/session indexes and can misdirect party, guild, whisper or persistence operations.

**Recommended fix:** Require an authenticated account/session, enforce a normalized Unicode policy and slot count, validate class/customization against allowlists, and reserve names atomically. Because names are embedded in arrays, a dedicated normalized-name collection with a unique index and transaction is safer than the current multikey index.

**Required tests:** Empty/long/control/confusable names, invalid class/look, ninth character, case-insensitive race and rollback when save creation fails.

### AUD-015 — Medium — TCP opcodes and chat lack practical abuse controls

**Evidence:** `GameServer.handleConnection` accepts every socket without per-IP/global connection limits (`src/server/core/server.ts:55-66`). `Client` caps buffered bytes and queued packet count, but `PacketRouter` has no authentication gate or per-opcode rate budget (`src/server/network/packetRouter.ts:36-76`). Public, party, private and guild chat accept protocol strings and broadcast/forward them without a shared message-length or token-bucket policy; public chat can also invoke the Discord relay (`src/server/handlers/SocialHandler.ts:1320-1365`).

**Impact:** Attackers can create connection floods, repeatedly invoke expensive persistence/broadcast handlers, spam large chat messages and amplify traffic to all level participants or Discord. Queue caps limit one symptom but do not protect CPU, database or outbound bandwidth.

**Recommended fix:** Add connection admission limits, idle/auth timeouts and global/per-IP ceilings. Define authentication and gameplay-state prerequisites for every opcode. Apply per-client token buckets by class (login, movement, combat, chat, persistence), strict field lengths and outbound backpressure. Rate-limit external bridge calls independently.

**Required tests:** Connection flood, unauthenticated opcode sweep, sustained chat, oversized strings, expensive-save spam and slow receiving peers.

### AUD-016 — Medium — Development password reset defaults on outside production

**Evidence:** `Config.ALLOW_DEV_PASSWORD_RESET` defaults to `process.env.NODE_ENV !== 'production'` (`src/server/core/config.ts:237`) and does not also require local/single-player mode. The `/lostpw` route permits a caller who knows an unlinked email to submit a replacement password when enabled (`src/server/core/StaticServer.ts:531-602`). Non-container multiplayer scripts can set `MULTIPLAYER_MODE=true` without setting `NODE_ENV=production`.

**Impact:** A multiplayer deployment started through the wrong script/environment exposes unauthenticated password replacement. The form also has no CSRF token.

**Recommended fix:** Default this feature off whenever multiplayer is enabled. Require an explicit local-only flag, bind only to loopback, print a prominent startup warning, and refuse startup if enabled on a public bind. Production recovery should use one-time expiring account-bound tokens or verified Discord delivery, with CSRF protection and throttling.

**Required tests:** Every combination of multiplayer, bind host, `NODE_ENV` and explicit flag; public binds must fail closed.

### AUD-017 — Medium — Empty level scopes retain displaced enemies

**Evidence:** `AILogic.updateLevel` returns immediately when no players are present (`src/server/core/AILogic.ts:271-300`), so its later debounced home reset is never applied. `test/combat_ai_regression.ts` fails because an enemy at X=75 remains there instead of returning to spawn X=5 and sleeping.

**Impact:** The next player/party entering an existing scope can inherit displaced enemies, stale aggro and inconsistent room state. This can create immediate attacks, missing encounters or irreproducible multiplayer behavior.

**Recommended fix:** On an empty scope, iterate live canonical NPCs through the debounced reset (or schedule one reset at scope-empty transition) before idling the scope. Clear target tokens and pending combat state, while preserving authored drama states.

**Required tests:** Keep the failing empty-scope test and add leave/rejoin with two players, active boss exceptions, cutscene NPCs and scope destruction.

### AUD-018 — Medium — A required client patch is missing and verification is incomplete

**Evidence:** `npm run verify:client-patches` checks 122 scripts and fails because `patch-dungeonblitz-forge-tutorial-persistence.ts` reports `restore=false persist=false`. `test/forge_tutorial_persistence_regression.ts` fails for the same reason. The patch script currently refuses normal application because its last tested implementation crashes the client at world enter, so this is an acknowledged unresolved client defect rather than a safe one-command repair. Thirty-seven FFDec-dependent patches could not be inspected on this host. The baseline file also allowlists 21 historically failing verifiers.

**Impact:** Forge tutorial completion is not persisted/restored as intended. More broadly, a large portion of binary behavior cannot be asserted by the current environment, and baseline failures can hide genuine lost functionality.

**Recommended fix:** Debug the forge patch with a debug Flash player, implement a non-crashing persistence path, apply it, and require both its focused regression and verifier. Provide FFDec in a pinned CI tool image and make unavailable checks fail protected release jobs. Triage every baseline entry into deliberate-revert versus defect; remove repaired entries promptly.

**Required tests:** Full verifier with zero unavailable checks, focused client regressions, clean-client world entry, forge tutorial complete/restart/restore, and checksums for every served SWF/SWZ.

### AUD-019 — Medium — Network-interface discovery can crash startup and tests

**Evidence:** `MULTIPLAYER_HOST` calls `resolveDefaultMultiplayerHost()` as the fallback argument to `parseStringEnv` (`src/server/core/config.ts:151-176`). JavaScript evaluates that fallback even when `MULTIPLAYER_BASE_IP` is explicitly set and even when multiplayer is disabled. `resolveDefaultMultiplayerHost` does not catch `os.networkInterfaces()` errors. In the restricted validation environment, every server import failed with `uv_interface_addresses returned Unknown system error 1` until the suite was run outside the sandbox.

**Impact:** A restricted container, platform error or permission policy can prevent the server, CLI tools and tests from starting for a feature they may not use.

**Recommended fix:** Resolve the explicit environment value first. Only enumerate interfaces when multiplayer is enabled and no explicit host exists, wrap enumeration in `try/catch`, log a warning, and fall back to localhost/a required configuration error as appropriate.

**Required tests:** Stub `os.networkInterfaces` to throw for single-player, explicit-host multiplayer and implicit-host multiplayer.

### AUD-020 — Medium — CI omits the checks that currently fail

**Evidence:** `.github/workflows/ci.yml` installs, typechecks and builds only. It does not run `npm run test:regression`, `npm audit --omit=dev`, `npm run verify:client-patches`, JSON/data checks or a production-container smoke test. The current branch builds successfully while four regression files and the patch gate fail.

**Impact:** Known authentication, multiplayer and client-asset regressions can merge and deploy despite a green required CI job.

**Recommended fix:** Make typecheck, build, all regressions, production dependency audit and full patch verification required checks. Use a pinned Node 22 + FFDec image. Build the production container, start it with disposable configuration, probe health and terminate it. Preserve failure logs as artifacts.

**Required tests:** Add a CI self-test or branch protection review that proves a failing regression and missing client patch block merge/deploy.

### AUD-021 — Medium — Production containment is weak

**Evidence:** `Container/Containerfile` has no `USER`, so Node runs as root. `Container/deploy-prod.sh` uses host networking and a writable bind mount for server data, with no read-only root filesystem, capability drop, resource limits or healthcheck-driven rollback. The service and legacy game protocol use plain HTTP/TCP by default.

**Impact:** A server-process compromise has unnecessary filesystem privilege, direct access to the host network namespace and write access to persisted game data. Resource exhaustion is not contained. Browser/account integration metadata may traverse an unencrypted public edge unless an external proxy is configured correctly.

**Recommended fix:** Run as a dedicated numeric non-root user, drop all capabilities, use a read-only root filesystem with explicit writable data/temp volumes, avoid host networking, publish only TCP 80/8080/843 as required, and set CPU/memory/PID limits. Put HTTP/OAuth routes behind TLS and a trusted reverse proxy with explicit proxy trust. Add backups and tested restore.

**Required tests:** Container runs non-root with read-only root, starts with only declared writable paths, survives health/restart tests and cannot reach unintended host services.

### AUD-022 — Medium — Active sockets can block graceful shutdown indefinitely

**Evidence:** `GameServer.stop` and `PolicyServer.stop` call `server.close()` but do not track/close active sockets (`src/server/core/server.ts:40-53`, `src/server/network/policyServer.ts:40-54`). `StaticServer.stop` likewise waits for open HTTP connections before closing integrations (`src/server/core/StaticServer.ts:1053-1070`). `main.ts` waits for all stop promises.

**Impact:** A connected or deliberately idle client can prevent deployment shutdown from completing, leading to forced termination, overlapping instances or lost deferred saves.

**Recommended fix:** Stop accepting connections, notify/flush authenticated clients, wait a bounded grace period, then destroy tracked sockets and close integrations/database clients. Add an overall shutdown deadline and idempotent signal handling.

**Required tests:** Shutdown with idle TCP, partial packet, keep-alive HTTP, active save and repeated signals must finish within the configured deadline.

### AUD-023 — Low — Development-only dependency has a high advisory

**Evidence:** Full `npm audit` reports high-severity advisory `GHSA-rgw5-rvv9-x895` for `brace-expansion` through `nodemon -> minimatch -> brace-expansion`. `npm audit --omit=dev` reports zero vulnerabilities, and the production container installs with `--omit=dev`.

**Impact:** The vulnerable package is not present in the production image, but malicious/untrusted glob input in development tooling could cause denial of service and the red full audit can hide future production findings.

**Recommended fix:** Update `nodemon`/`minimatch` to a dependency set containing the patched `brace-expansion`, regenerate the lockfile, and keep separate required production and monitored full audits.

### AUD-024 — Low — Lockfile root-package versions were stale

**Evidence:** Before this report, both lockfiles had top-level version `1.27.0` while `packages[""].version` remained `1.23.0`.

**Impact:** Release tooling or SBOM generators that read the package record can report inconsistent versions.

**Recommended fix:** Keep all four manifest/lockfile package records synchronized as part of version bump automation. This report's `1.27.1` patch bump corrects the drift.

### AUD-025 — Low — Flash socket policy is overbroad

**Evidence:** Both `src/server/core/Client.ts` and `src/server/network/policyServer.ts` return a policy granting `domain="*"` access to `to-ports="1-65535"` with `secure="false"`, although the game needs only its configured game port.

**Impact:** Any hosted Flash content can open socket connections through the user's runtime to any port allowed by the policy. This unnecessarily expands the client-origin trust boundary.

**Recommended fix:** Serve a single policy limited to the exact game domain(s) and configured TCP port. Remove the duplicate policy implementation and document whether the legacy client requires insecure transport.

### AUD-026 — Low — Security and hosting documentation is stale

**Evidence:** `docs/SECURITY.md` lists `0.9.x` twice, once supported and once unsupported, while the project is at `1.27.x`. It provides only a Discord-ticket sentence and no supported deployment/security contact detail. `docs/HOSTING.md` describes a manual Podman/tmux flow that does not cover current Mongo, Discord, TLS, proxy trust, production environment or hardening requirements. `.env.example` documents `TRUST_PROXY_HEADERS`, but the application ignores it.

**Impact:** Operators can deploy an insecure configuration and reporters cannot determine support status or safe disclosure expectations.

**Recommended fix:** Publish accurate supported versions, a private reporting channel, response expectations and a production hardening guide. Generate or test environment documentation against the actual `Config` schema so dead settings are detected.

### AUD-027 — Informational — Production dependencies and data baseline

`npm audit --omit=dev` reports zero production vulnerabilities across 99 production dependencies. Seventy-two tracked JSON files were parsed during the audit; `src/server/data/EntTypes.json` contains a UTF-8 BOM and requires BOM normalization, which the runtime data path currently tolerates. Existing loaders successfully loaded 1,647 entity types, 185 levels, 219 doors, 293 missions and the tested associated data during regressions.

Keep these as explicit CI checks. Consider removing the BOM so strict generic JSON tooling also succeeds.

## Recommended remediation order

1. **Immediate containment:** Do not expose the current multiplayer service to untrusted clients. Preserve logs/backups, disable public account-link routes, and communicate that existing credentials/session data may be affected.
2. **Identity boundary:** Fix AUD-001 through AUD-004 together. Invalidate existing transfer/pending OAuth tokens and review Discord links created through the unauthenticated route.
3. **Gameplay authority:** Fix AUD-005 through AUD-010. Introduce shared authoritative mutation primitives rather than adding packet-specific clamps.
4. **Social and persistence:** Fix AUD-011 through AUD-014, then audit existing duplicate names/Discord links and add save revisions/backups before migration.
5. **Abuse and operations:** Add the controls in AUD-015 through AUD-022 and deploy behind a hardened, observable edge.
6. **Release gate:** Make all currently failing validations required, supply FFDec in CI, and do not cut a public multiplayer release until the regression suite and client-patch gate are fully green.

## Definition of done for a safe multiplayer release

- No packet can assign or change `userId`, account or character identity without an authenticated, account-bound, one-time server credential.
- All combat, health, rewards, progression, inventory and party mutations are derived or authorized by server state.
- Every cross-player action has an explicit ownership/consent/team policy and a two-client adversarial regression.
- Character persistence uses revisions/transactions and passes concurrent update/failure-injection tests.
- Password, OAuth, linking and reset flows pass replay, NAT, proxy and rate-limit tests.
- All 92 current regressions pass, the lost forge behavior is resolved, and every client patch is checkable in CI.
- Production runs non-root behind TLS with explicit trusted-proxy configuration, connection/resource limits, bounded shutdown and tested backups.
